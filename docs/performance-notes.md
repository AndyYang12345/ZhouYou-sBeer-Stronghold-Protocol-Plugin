# 性能笔记：为什么"每帧改单位变换"会明显拖慢这个游戏

这份笔记记录一轮完整的性能排查，结论都是**实测**得出的，不是推测。
如果你要写一个每帧改渲染对象的插件，这几条能直接省掉你几小时。

---

## 一、先分清"谁的成本"

进战斗时的耗时由三部分构成，**只有分开量才知道该优化哪一部分**：

| 来源 | 性质 | 能否避免 |
|---|---|---|
| 游戏加载 PIXI + pixi-spine | 按需加载（`app.js` 注释 *loaded on demand*） | ❌ 游戏固有 |
| 游戏首次解码单位/敌人贴图 | `Decode Image` 累计约 250ms | ❌ 游戏固有 |
| 插件每帧改写渲染对象 | 自己的开销 | ✅ 该优化的部分 |

实测（Chrome 性能追踪，69 秒，4 次长任务 105/267/363/267 ms）里，
这 4 次长任务的 CPU 时间几乎全是 `Decode Image` + `RunMicrotasks` + GC；
而插件在其中只占 **0.02~0.07ms**。

**但**——用户装"空模组"（`client.js` 只有一行 `console.log`）时进战斗 1 秒内完成，
装本插件则明显更慢。**所以插件确实有害，只是它的害处不在长任务里，而在每帧的持续开销。**

> ★ 教训：**别只看长任务里自己的占比就下结论**。持续性的每帧开销不会出现在长任务里，
> 却能实打实地拖慢整个加载过程。**A/B 对照（空插件 vs 真插件）比任何静态分析都有力。**

---

## 二、两处真正的浪费（都在"没跟上游戏的优化"）

### 1. 不要碰被裁切的单位

宿主在 `public/js/render/units.js:1690` 的 `_cull()` 里，对**屏幕外**的单位：

```js
this.root.visible = !off;      // 直接隐藏
if (off) this._offDt += dt;    // 而且不推进它的动画，等回到视野再补
```

也就是说游戏对屏幕外的单位**既不画也不动画**。插件如果照旧给它们写变换：

- 纯浪费（那些变换没有任何人会看到）；
- 更糟的是**占掉了你自己的每帧预算**，让屏幕里真正需要的单位排不上。

判据：`view.culled === true` 或 `view.root.visible === false`。

### 2. 加载期让路（用宿主自己的负载判据）

进入战斗时游戏在解码贴图、建骨架、算 impostor 框，主线程本来就满。
此刻再塞每帧写入，只会把那一帧推得更长。

宿主**自己就有"设备吃紧"的判据**（`public/js/render/app.js:1847` 的 `adaptLoad`）：

```js
const busy = views.size + penViews.size > 8;
if (frameMs > 19.5 && busy) slowFor += dtRaw;      // 帧时间超 19.5ms 就累积
if (slowFor > 1 && loadLevel < 3) loadLevel++;     // 持续 1 秒就升到 1~3 级
```

通过 `view.stats().lod` 就能读到这个等级。**它 ≥2 说明游戏已经认为设备吃紧 ⇒ 插件也该让路**，
等它降下来再恢复。这不是"关特效"，只是那段时间不写，恢复是无感的。

> ★ 这一条尤其值得注意：游戏在**高负载时反而会画得更多**
> （`units.js` 抬头：*from level 2 on every unit does* = 本来隔帧动画的单位变成每帧都动）。
> 所以插件推高 `frameMs` 会让游戏进入更费的状态，形成负反馈。

## 三、帧驱动方式（照抄参考实现，别自己发明）

参考实现（CyanFish Stronghold-Protocol-CyanModPack，`dj-all/client/engine-pixi.js`）
在这几点上都是明确结论：

```js
/** 挂到宿主 ticker 的优先级（PIXI v7 按 priority 降序；
 *  宿主自己的 frame 是 NORMAL(0)、渲染在 LOW(-25)）。 */
export const TICK_PRIORITY = -20;
ticker.add(tick, null, TICK_PRIORITY);
```

顺序因此是确定的：

```
宿主更新单位位置(0) → 插件写入变换(−20) → 渲染(−25)
```

- **用默认优先级 0（与宿主同级）顺序不确定**：可能先写后被宿主覆盖，也可能写完等一帧才渲染。
  "时好时坏"正来自这种不确定性。
- **挂上 ticker 后要停掉自建 rAF**，否则每帧多一次回调。
- 它有 `BUDGET = 400` 的每帧写入上限 —— 固定预算保证特效永远不会成为掉帧主因。

## 四、把动画写成"纯时间函数"，而不是有状态的积分

这是参考实现最值得抄的一点。它每帧直接由时刻算出姿态：

```js
s = squashProfile(t / Tq)          // 三角波：40% 压 + 40% 弹 + 20% 停
yK = 1 - (1 - M) * s               // 高度
xK = 1 + (W - 1) * s               // 宽度
axisK = cos(theta)                 // 竖直轴：宽度乘 cos θ（允许为负 ⇒ 镜像）
```

写回用 `MODE_FREE` 语义（第一次碰到时记下原值当基准，之后写 `基准 × 系数`）。

**相比"弹簧积分"的好处**：

| | 有状态（弹簧） | 纯时间函数 |
|---|---|---|
| 漂移 | 会累积 | **不会**（绝对计算） |
| 同步 | 需要共享时基 + 死区 + 收敛调参 | **天然同相**（都读同一个 `t`） |
| 省写入 | 要阈值/量化/台阶 | **不需要**（基准只记一次） |
| 掉帧 | 累积误差 | 不累积 |

**结论：如果观感允许，优先写成纯时间函数。** 它会一次性消掉一整类问题。

## 五、热路径不要分配

每帧每单位返回一个新对象，在 200Hz × 20 单位下就是**每秒 4000 个短命对象**，
直接推高 GC 压力（实测追踪里 GC 约占 180ms）。

```js
// 不要
return { x: ..., y: ... };
// 要（复用同一个对象；调用方必须立即读取，不可保存引用）
const OUT = { x: 1, y: 1 };
OUT.x = ...; OUT.y = ...; return OUT;
```

同理，每帧收集列表也不要新建数组，传一个复用缓冲进去。

## 六、排查方法本身

按"证据强度"排序：

1. **A/B 对照**（最有力）：做一个**空插件**当对照组。如果空插件也慢 → 问题在插件系统/游戏；
   如果空插件快、真插件慢 → 确定是插件。**这一步能在几分钟内排除掉一半可能性。**
2. **浏览器性能录制 + 读 trace**：能给出"哪个函数、哪一行、多少毫秒"。
   `RunTask` 里找 `FunctionCall`，配上 `args.data.url` 就知道是哪个脚本。
3. **宿主自带的 stats**：`__SP_VIEW__.raw.stats()` 给出 `fps / frameMs / cpuMs / lod / units /
   impostor / culled` —— 判断"游戏自己怎么看当前负载"的最佳来源。
4. 自己的埋点（`performance.now()` 差值）。

> ★ **无头浏览器的结论不可信**：它的软件渲染路径、资源加载时机都与真实环境不同。
> 实测同一段代码在无头里那个"2 秒尖峰"在**没装插件**时也照样出现。
> 真实环境的结论必须以真机测量为准。
